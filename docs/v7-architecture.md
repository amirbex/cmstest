# AtoZ Content Studio v7 — راهنمای معماری و کار

این نسخه از پایه روی **مدل واقعی پلن محتوایی شما** ساخته شده است، نه روی یک ساختار فرضی.
هر تصمیم معماری در این سند با ارجاع به همان فایل پلن توجیه شده است.

---

## ۱. مدل داده

فایل پلن شما سه سطح دارد و برنامه همان سه سطح را ذخیره می‌کند:

```
batch  (ATZ-B-M01-W01-P1)
  └─ idea      19 ایده، هرکدام یک content_id      → جدول idea
       └─ plan_asset   25 دارایی (کاروسل، ریلز، ابزار وب…) → جدول plan_asset
            └─ publish   48 انتشار زمان‌بندی‌شده      → جدول publish
```

**چرا این تفکیک؟** در پلن شما ۱۹ ایده به ۲۵ دارایی و ۴۸ انتشار می‌رسند. یک ایده می‌تواند
همزمان در اینستاگرام، تلگرام و سایت منتشر شود و هر انتشار کپشن، تایم‌لاین، اسلاید و
داده‌های عملکرد خودش را دارد. اگر این‌ها را در یک ردیف فشرده کنیم (کاری که نسخهٔ ۶ می‌کرد)
دیگر نمی‌توانیم بگوییم «این ریلز در تلگرام بهتر جواب داد تا در اینستاگرام».

| جدول | نقش |
|---|---|
| `idea` | ایدهٔ محتوایی: عنوان، ستون (P1..P6)، رشته، پرسوناها |
| `plan_asset` | دارایی تولیدی: نوع، نام، محل ذخیره، کدهای زیرفایل نسخه‌دار |
| `publish` | یک رویداد انتشار روی یک پلتفرم در یک زمان |
| `snapshot` | آمار خام یک انتشار در یکی از سه پنجره (۲۴ ساعت / ۷ روز / ۳۰ روز) |
| `edit_document` | سند تدوین: صحنه‌ها، زمان‌بندی و متن قابل ویرایش |
| `media` | فایل‌های آپلودی و مشتقات (فشرده‌شده، زیرنویس‌خورده) |
| `transcript` | زیرنویس: cueها و زمان‌بندی واژه‌به‌واژه |

جدول‌های قدیمی `content` / `delivery` / `asset` دست‌نخورده مانده‌اند تا موتور رندر
نسخهٔ ۶ که هنوز از آن‌ها استفاده می‌کند نشکند.

## ۲. کلید تقویم (schedule key)

```
M01-W01-D01-IG-CAR-04
│   │   │   │  │   └─ شماره ترتیب در آن روز
│   │   │   │  └───── کد فرمت (CAR, REL, MNR, MCR, STG, CHN, LIB, MAG, PRM, CLC…)
│   │   │   └──────── کد پلتفرم (IG, TG, YT, WEB)
│   │   └──────────── روز هفته (۰۱ = شنبه … ۰۷ = جمعه)
│   └──────────────── هفتهٔ ماه
└──────────────────── ماه
```

**قاعدهٔ اصلی:** `scheduled_for` هیچ‌وقت مستقل ذخیره نمی‌شود — همیشه از کلید تقویم و
لنگر هفتهٔ همان بچ بازمحاسبه می‌شود. یعنی وقتی انتشار را جابه‌جا می‌کنی، فقط کلید عوض
می‌شود و زمان واقعی خودش دنبالش می‌آید. این جلوی کلاسیک‌ترین باگ تقویم‌ها را می‌گیرد:
«کلید می‌گوید پنجشنبه ولی تاریخ می‌گوید چهارشنبه».

`parseScheduleKey` علاوه بر شکل، **بازه‌ها** را هم بررسی می‌کند:

- `D08` رد می‌شود (فقط هفت روز داریم)
- `M13` رد می‌شود
- `W06` رد می‌شود

بدون این بررسی، یک غلط تایپی یک اسلات تقویمی می‌ساخت که هیچ تقویمی نمی‌توانست حلش کند.

## ۳. شاخص‌ها (KPI)

تفکیک سخت‌گیرانه، و دلیلش:

- **ورودی کاربر فقط آمار خام است**: ریچ، لایک، کامنت، ذخیره، کلیک، زمان تماشا…
- **هیچ نرخ و شاخصی از سمت کلاینت پذیرفته نمی‌شود.** فرمول‌ها فقط در `computeKpis()` هستند.

اگر نرخ‌ها را از سمت مرورگر قبول کنیم، یک اشتباه تایپی در «ذخیره» به‌شکل یک KPI معتبر
در داشبورد ظاهر می‌شود و بعد تصمیم استراتژیک بر مبنای آن گرفته می‌شود. تقسیم بر صفر هم
همیشه `null` برمی‌گرداند، نه `Infinity`.

**شاخص کیفیت انسانی** میانگین برابر چهار محور است، و فقط محورهایی که واقعاً امتیاز
گرفته‌اند در میانگین شرکت می‌کنند — یک محور امتیازنگرفته میانگین را به سمت صفر نمی‌کشد.

## ۴. خط لولهٔ زیرنویس

```
آپلود  →  probe  →  فشرده‌سازی (CRF 26)  →  استخراج صدا (mono 16kHz)
                                    →  Gemini با اسکیمای واژه‌به‌واژه
                                    →  پاک‌سازی زمان‌بندی (بدون هم‌پوشانی)
                                    →  موتور زیرنویس خودمان (ASS + ffmpeg)
```

**چرا اول فشرده‌سازی؟** یک کلیپ موبایلی ۲۰۰ مگابایتی هم آپلود را کند می‌کند، هم
رونویسی را، هم رندر را. رمزگذاری دوباره با CRF 26 روی همان رزولوشن معمولاً ۶۰ تا ۸۵
درصد حجم را کم می‌کند بدون افت قابل‌دیدن. در تست واقعی روی یک کلیپ ۱۰۸۰×۱۹۲۰:
**۶۵.۷ درصد کاهش (۴۴۱ کیلوبایت → ۱۵۱ کیلوبایت)**.

**رندر زیرنویس با ASS، نه فیلتر سادهٔ `subtitles=`**: چون ASS موقعیت هر cue، حاشیهٔ
تیره و پیل پس‌زمینه می‌دهد — همین سه چیز است که زیرنویس فارسی را روی فوتیج شلوغ خوانا
می‌کند. حالت کارائوکه هر واژه را یک خط جدا می‌نویسد تا با زمان دقیق خودش ظاهر شود.

**صداقت در برچسب‌گذاری:** وقتی کلید مدل نیست یا مدل صدا را نمی‌شنود، از متن نریشن یک
زمان‌بندی *برآوردی* ساخته می‌شود و ترنسکریپت با `source: "estimated"` برچسب می‌خورد.
رابط کاربری هم همین را نشان می‌دهد: «زمان‌بندی برآوردی». هیچ‌جا ادعا نمی‌کنیم رونویسی
کرده‌ایم وقتی نکرده‌ایم.

اگر فایل اصلاً صدا نداشته باشد، صریح خطای `NO_AUDIO_STREAM` با پیام فارسی برمی‌گردد،
نه یک خطای مبهم ffmpeg.

## ۵. کتابخانهٔ قالب‌ها — چرا ۱۲۰۰ و نه ۴۰۰

رسپی‌ها به‌جای کپی‌پیست، از محورهای متعامد **ساخته** می‌شوند:

```
intent   (۱۴)  ×  motion (۸)  ×  layout (۴)  ×  style (۳)   →  ۱۲۰۰ رسپی
چه چیزی        چگونه وارد       چگونه چیده     چگونه تایپ
```

**مزیت این روش بر ۴۰۰ اسنیپت دستی:**

1. **همه واقعاً قابل رندرند** — هر محور به یک primitive موجود نگاشت می‌شود
   (`MOTIONS`، `buildCover`، `buildCarouselSlide`، `buildReelScene`).
2. **شناسه‌ها قطعی‌اند** — `cover.fade.editorial.navy` همیشه همان است، پس ارجاع ذخیره‌شده
   پس از ری‌استارت هم معتبر می‌ماند.
3. **توسعه یک‌خطی است** — برای ۱۵۰ رسپی جدید، یک preset به `MOTIONS` اضافه کن؛ لازم نیست
   ۱۵۰ فایل بسازی و نگه داری.
4. **فیلترها زنده‌اند** — تعداد هر وجه از همان کاتالوگ شمرده می‌شود، پس هیچ فیلتری نتیجهٔ
   خالی ندارد.

خانواده‌های پوشش‌داده‌شده: `core`، `opendesign`، `remotion-skills`، `hyperframes`،
`anatomy`، `motion-library`.

## ۶. صف تولید — از ایده تا کانسپت زمان‌بندی‌شده

مسیر دقیقی که خواسته بودید («ایدهٔ اصلی + راهنمای ساخت ← کانسپت ریلز زمان‌بندی‌شده،
قابل ویرایش»):

```
publish  →  buildConcept(deliveryId, guideId)
              │
              ├─ متن از خود پلن: timeline → slides → کپشن (به همین ترتیب اولویت)
              ├─ شکل از راهنمای ساخت: قلاب/مسئله/راه‌حل/دعوت، سه‌گام، باور غلط، قبل‌وبعد…
              └─ زمان‌بندی: وزن هر beat × مدت کل، انباشت کسری و گرد کردن
                    ↓
              edit_document  (صحنه‌ها، startSec/endSec، متن، رنگ، گذار)
                    ↓
              استودیو تدوین  →  ویرایش  →  ذخیره
```

**قاعدهٔ نامتغیر:** صحنه‌ها همیشه تایم‌لاین را بدون شکاف پر می‌کنند. تغییر مدت یک صحنه،
مدت صحنهٔ بعد را به‌اندازهٔ همان اختلاف جابه‌جا می‌کند. رندرکننده به این قاعده تکیه می‌کند
و بدون آن، انتهای ویدیو سیاه می‌شد.

**هیچ متنی ساخته نمی‌شود.** راهنمای ساخت فقط *شکل* را تعیین می‌کند؛ جمله‌ها از تایم‌لاین،
اسلایدها و کپشن خودِ پلن می‌آیند. اگر پلن سه beat بدهد و راهنما شش beat بخواهد، وزن‌ها
ادغام می‌شوند نه اینکه نوشتهٔ شما دور ریخته شود.

## ۷. ساختار کد

```
packages/contracts/src/index.ts     ← تک‌منبع حقیقت برای انواع و اعتبارسنجی
app/server/src/
  lib/db.js                         ← ۲۱ جدول؛ مایگریشن غیرمخرب
  lib/http.js                       ← روتر بدون وابستگی + بدنهٔ باینری‌امن + multipart
  engine/templates.js               ← کاتالوگ ۱۲۰۰ رسپی از محورهای متعامد
  services/plan.js                  ← ingest، تقویم، شاخص‌ها، تحلیل
  services/production.js            ← ایده → کانسپت → سند تدوین، صف تولید
  services/media.js                 ← probe، فشرده، زیرنویس، رندر ASS
  services/subtitles.js             ← رونویسی Gemini + اعتبارسنجی زمان‌بندی
  routes/{plan,media}.js            ← ۴۵ مسیر جدید (۱۸ پلن، ۴ قالب، ۱۰ تولید، ۱۳ رسانه)
app/web/src/rooms/
  Dashboard.tsx  Calendar.tsx  Production.tsx  Editor.tsx  Templates.tsx
  Assets.tsx     Insights.tsx
```

### تصمیم‌های ریز که ارزش دانستن دارند

- **`http.js` بدنه را همیشه به‌صورت Buffer می‌گیرد.** نسخهٔ قبل مستقیم UTF-8 می‌کرد؛
  یک بایت نامعتبر کل ویدیو را خراب می‌کرد. حالا `ctx.rawBody` خام است و `body` فقط
  وقتی پارس می‌شود که نوع محتوا ساخت‌یافته باشد.
- **`/api` هرگز از فایل‌های استاتیک سرو نمی‌شود.** وگرنه fallback برنامهٔ تک‌صفحه‌ای
  پاسخ یک مسیر API را می‌دزدید.
- **پوشهٔ `assets/` روی `/files` سرو می‌شود، نه `/assets`** — چون `/assets` مسیر باندل
  Vite است و مانت کردن روی آن، کل رابط را می‌شکست.
- **محدودیت بدنه ۵۱۲ مگابایت** تا آپلود کلیپ واقعی ممکن باشد.

## ۸. اجرا

```bash
npm install
npm run seed          # داده نمونه (اختیاری)
npm run dev           # API روی ۴۰۰۰ + Vite روی ۵۱۷۳
```

تک‌پورت (نصب محلی):

```bash
npm run build
npm start             # http://localhost:4000 — UI و API از یک پورت
```

کلید مدل (اختیاری؛ بدون آن همه‌چیز آفلاین کار می‌کند، فقط رونویسی «برآوردی» می‌شود):

```bash
echo 'GEMINI_API_KEY=...' > .env
```

### وارد کردن پلن

۱. داشبورد → «انتخاب فایل پلن JSON» → فایل `ATZ-B-M01-…ContentPlan.json`
۲. یا با API:

```bash
curl -X POST localhost:4000/api/plan/ingest \
  -H 'content-type: application/json' \
  -d "{\"plan\": $(cat docs/reference/ATZ-B-M01-W01-P1_ContentPlan.json), \"weekStartIso\": \"2026-11-14\"}"
```

Ingest **ایدمپوتنت** است: اجرای دوباره همان فایل، ردیف تکراری نمی‌سازد؛ تفاوت‌ها را
به‌صورت `added/updated` گزارش می‌کند.

## ۱۰. آنچه هنوز نیست

صادقانه، تا انتظار واقعی با واقعیت هم‌تراز بماند:

- **موتور رندر ویدیوی مبتنی بر Remotion / HyperFrames** پیاده نشده. کاتالوگ و برچسب‌های
  خانواده‌ها آماده‌اند و به primitive های موتور فعلی (Canvas + ffmpeg) نگاشت می‌شوند، اما
  خودِ کتابخانه‌های خارجی نصب نشده‌اند. برای این کار باید API آن‌ها خوانده شود.
- **آپلود مستقیم از سمت کلاینت به Gemini** با فایل‌های بزرگ‌تر از ۲۰ مگابایت نیاز به
  File API گوگل دارد؛ فعلاً مسیر inline برای کلیپ‌های کوتاه پیاده شده است.
- **زمان‌بندی واژه‌به‌واژه فقط با کلید مدل** به‌دست می‌آید؛ در حالت آفلاین برآوردی است و
  همین‌طور برچسب می‌خورد.
